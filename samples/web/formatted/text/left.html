Writing release notes

Release notes tell users what changed and why it matters. Keep each entry to one or two sentences—readers skim them.

Draft: ask the support team which fixes they were asked about most.

Mark breaking changes clearly, link to the migration guide, and name settings exactly, such as sync.interval. (Screen reader hint: settings are case sensitive.)

Plain text keeps characters that Markdown would read: use * or _ for emphasis, a # for a heading, a | between table cells, and [brackets] for links.

1. A line that starts like a numbered step is still a paragraph.

Good release notes answer three questions:

  • What can I do now that I could not before?
  • What works differently?

Steps

  1. Collect the merged changes.
    • Leave out internal refactoring.
    • Group fixes by area:
      • Sync
      • Search
  2. Write one entry per change.
  3. Ask a second person to read them.

Terms

Breaking change
A change that makes existing notes, settings or scripts stop working.
Deprecation
A feature that still works but will be removed in a later release.

Example settings

[sync]
interval = 5        # minutes
retry = true

[search]
instant = false

Long entries are hard to scan: when a paragraph runs past three lines, readers miss the one sentence they were looking for, so put the most important change first and leave the background for the linked article.
