Writing release notes

Release notes tell users what changed and why it matters. Keep each entry to one or two sentences—readers skim them.

Draft: check the wording with the documentation team before publishing.

Mark breaking changes clearly, link to the migration guide, and name settings exactly, such as sync.interval_minutes. (Screen reader hint: settings are case sensitive.)

Plain text keeps characters that Markdown would read: use * or _ for emphasis, a # for a heading, a | between table cells, and [brackets] for links.

1. A line that starts like a numbered step is still a paragraph.

Press Ctrl+S (⌘+S on macOS) to save; Esc closes the dialog. Write a setting with backticks in it as `name`.

Good release notes answer three questions:

  • What can I do now that I could not before?
  • What works differently?
  • What do I need to do?

Steps

  1. Collect the merged changes.
    • Leave out internal refactoring.
    • Group fixes by area:
      • Sync
      • Search and filters
      • Accessibility
  2. Write one entry per change, starting with a verb.
  3. Ask a second person to read them.
  4. Publish them with the release.

Terms

Breaking change
A change that makes existing notes, settings or scripts stop working.
Deprecation
A feature that still works but will be removed after two releases.

Example settings

[sync]
interval_minutes = 10
retry = true

[search]
instant = true

Long entries are hard to scan: when a paragraph runs past three lines, readers miss the one sentence they came for, so put the most important change first and leave the background for the linked article.
