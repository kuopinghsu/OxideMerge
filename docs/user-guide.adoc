[.lead]
OxideMerge is a visual tool for comparing and merging files and folders.
It runs on Windows, macOS and Linux.
Use it to review changes, combine edits and resolve merge conflicts.
It also compares binary files, images and web pages.
OxideMerge is written in Rust and is inspired by WinMerge.

This guide is also available in xref:user-guide.zh-TW.adoc[繁體中文].

[[introduction]]
== Introduction

=== What OxideMerge does

* Compare two or three folders, including archives. Copy, delete or merge the items.
* Compare and edit text files. Copy changes between versions and resolve version-control conflicts.
* Compare the bytes of binary files, the pixels of images and the content of web pages.
* Hide differences that do not matter with comparison options and reusable compare rules.
* Export reports and patches. Save projects and comparisons for a later review.
* Run comparisons from scripts, and use OxideMerge as the diff and merge tool for Git.

The interface is available in English, Traditional Chinese, Simplified Chinese, Japanese, Korean,
German, French, Spanish, Russian, Brazilian Portuguese and Italian.

=== How to use this guide

Start with <<first-comparison>> for a short walkthrough.
Then read the chapter for the kind of comparison you need.
The chapters at the end are reference material: the command line, options, keyboard shortcuts
and troubleshooting.

This guide uses these conventions:

* *Bold text* is a name that you see in the program, such as a button or a menu command.
* A menu path such as *File → Open...* means: open the *File* menu, then choose *Open...*.
* Command-line examples assume that `oxidemerge` is in your `PATH`.
  If it is not, use the full path of the program.
* Replace example paths, such as `old-folder`, with your own paths.

[NOTE]
====
*Keyboard shortcuts on macOS.* This guide uses the key names of Windows and Linux.
On macOS, press Command (kbd:[⌘]) instead of kbd:[Ctrl], and Option (kbd:[⌥]) instead of kbd:[Alt].
The one exception is kbd:[Ctrl+Tab], which uses the Control key on macOS too.
Menus and tooltips always show the shortcuts for your system.
====

=== Key terms

Side:: One version in a comparison: the left, middle or right version.
Pane:: The area of the window that shows one side.
Difference:: A place where the versions are not the same.
In a text comparison, one difference can include several lines.
Base (common ancestor):: The original version that two edited versions came from.
In a three-way comparison, the base is in the middle.
Conflict:: A place where both edited versions changed the same text in different ways.
You must choose or edit the result yourself.
Merge:: To copy or combine changes into a destination version.
Filter:: A rule that selects which files and folders a folder comparison includes.
Compare rule:: A rule that changes which text differences count.
It does not change the files.

IMPORTANT: A merge changes its destination.
Before you copy or save, check the source, the destination and the output path.
Make a side read-only if you only need to look at it.

== Installation

Download the package for your system and processor from
https://github.com/kuopinghsu/OxideMerge/releases[GitHub Releases].
Each release also includes this guide as a PDF file, in English and in Traditional Chinese.
The release page shows the SHA-256 digest of each download, so you can check the file.

[cols="1,3"]
|===
|System |Package

|Windows 10 or 11, x64 or Arm64
|`oxidemerge-<version>-windows-x64.zip` or `oxidemerge-<version>-windows-arm64.zip`

|macOS 11 or later
|`oxidemerge-<version>-macos-universal.dmg`, for Apple silicon and Intel

|Linux x64 or Arm64
|An AppImage (for Ubuntu 20.04, RHEL 8, Debian 10 and later) or a TAR.GZ archive.
Choose `linux-x64` for Intel and AMD processors, or `linux-arm64` for 64-bit Arm.
|===

=== Windows

Extract the ZIP file and run `oxidemerge.exe`. There is nothing to install.

=== macOS

. Open the DMG file and drag *OxideMerge* to *Applications*.
. Start OxideMerge.
  The app is signed ad hoc and is not notarized by Apple, so macOS can block the first start.
  If this happens, choose *Open Anyway* in *System Settings → Privacy & Security*.
  On macOS 14 and earlier, you can also Control-click the app and choose *Open*.

To start OxideMerge from Terminal, use the full path of the program.
To use the short command `oxidemerge`, create a link in a folder that is in your `PATH`.
For example:

[source,sh]
----
sudo ln -s /Applications/OxideMerge.app/Contents/MacOS/oxidemerge /usr/local/bin/oxidemerge
----

=== Linux

* Use a desktop session with X11 or Wayland.
* Make the AppImage executable before you start it: `chmod +x oxidemerge-*.AppImage`.
* If your system does not have FUSE, start the AppImage with `--appimage-extract-and-run`.
* File dialogs need `xdg-desktop-portal`. Most desktop environments include it.
* To show Chinese, Japanese and Korean text, install a CJK font, such as Noto Sans CJK.

=== Building from source

. Install a Rust toolchain from https://rustup.rs/.
. In the repository folder, run `cargo build --release --locked`.

The program is `target/release/oxidemerge` (`target/release/oxidemerge.exe` on Windows).
For the requirements and checks, see xref:development.md[the development guide].

== Getting started

=== The start page

When you start OxideMerge without a comparison, it shows the start page.

.The start page
image::start.png[Start page]

The start page has these parts:

Compare files or folders:: Enter a *Left* path and a *Right* path.
You can type a path, paste it, or click the file and folder buttons next to the field.
Click *3-way* to add a *Middle* path.
Click *More options…* to open the *Select files or folders* dialog with these paths.
Open conflict file:: Resolve a file that contains conflict markers. See <<conflict-files>>.
Release summary / Compare baselines:: Compare two folders or saved reviews as two releases.
See <<baselines>>.
Recent:: Your last comparisons, shown as cards.
+
--
* Click a card to run that comparison again.
* Right-click a card to change its paths (*Change paths...*) or remove it (*Remove from Recent*).
* Click *Clear*, at the right of the *Recent* heading, to empty the list.
  *File → Open recent → Clear recent comparisons* does the same.
  A message then offers *Undo* for a few seconds.
--

When the recent list is empty, for example on the first start, the start page shows
*Open a sample*.
This button opens two small sample folders, so you can see how comparisons work.
The sample folders are temporary: OxideMerge removes them when you close the tab, and does not
add the sample to the recent list.

[[first-comparison]]
=== Your first comparison

. On the start page, enter an older file as *Left* and a newer file as *Right*.
. Click *Compare*.
  To protect a side from changes, click *More options…* instead and turn on *Read-only* for that
  side.
. Press kbd:[Alt+↓] to go to the next difference.
. To copy a difference, check which pane is the destination.
  Then click the arrow that points to that pane.
. Check the result.
  To save it as a new file, choose *File → Save as*.
  To update the file in the pane, choose *Save*.

To review files without changing them, make both sides read-only.
To share your review without sending the files, export an HTML report (see <<reports>>).

=== The main window

The window has these parts:

Menu bar:: *File*, *Edit*, *View*, *Compare*, *Merge*, *Tools* and *Help*.
Commands that do not apply to the current tab are unavailable.
Title bar:: At the right end: *Search commands*, which opens the command palette, *Open*, a
switch for the light and dark themes, *Options* and *Help & Shortcuts*.
In a narrow window, the search field becomes an icon, and buttons that do not fit are hidden.
The menus have the same commands.
Tabs:: Each comparison opens in its own tab.
If both sides have the same file name, the tab shows the name once and then the folders that are
different.
A dot in place of the close button means that the tab has unsaved changes.
Move the pointer over the dot to close the tab.
Status bar:: Shows whether the sides are different and the current line or offset.
The interface language is at the right end.
The numbers of differences and items are shown in the toolbar and in the folder chips.

To work with tabs:

* kbd:[Ctrl+Tab] and kbd:[Ctrl+Shift+Tab] go to the next and the previous tab.
* kbd:[Ctrl+W] or kbd:[Esc] closes the current tab.
  If a dialog, search bar, preview or editor is open, kbd:[Esc] closes it first.
  If the tab has unsaved changes, OxideMerge asks before it closes the tab.
* Right-click a tab to close it, the other tabs, the tabs to its right, or all tabs.

To change the interface language, use *Options → General*, or start OxideMerge with `--lang`.

To see the version, click the app logo or choose *Help → About OxideMerge*.
The dialog also shows a build identifier:

* A development build shows a short Git hash.
  `-dirty` is added when tracked source files had uncommitted changes.
* A clean optimized build of a release tag shows its build date (UTC).

`oxidemerge --version` prints the same identifier.

=== Opening a comparison

You can start a comparison in several ways:

* On the start page, enter the paths under *Compare files or folders* and click *Compare*.
* Choose *File → Open...* (kbd:[Ctrl+O]), or click *More options…* on the start page.
  This opens the *Select files or folders* dialog.
* Drop two or three files or folders on the window.
  If you drop one item, the dialog opens with that item filled in.
* Choose a recent comparison on the start page, in *File → Open recent* or in the command palette.
* Start OxideMerge from the command line (see <<command-line>>) or from your file manager
  (see <<file-manager>>).

To use the *Select files or folders* dialog:

.The Select files or folders dialog
image::dialog.png[Select files or folders dialog]

. Enter or browse for the *Left* and *Right* paths.
  A path can be a file, a folder, or an address that starts with `http://` or `https://`.
  To compare three versions, turn on *3-way compare* and enter a *Middle* path.
. Turn on *Read-only* next to a side to protect it from changes.
  *Swap left/right* exchanges the two sides.
. For folders, choose *Include subfolders*, a *Filter* and a *Compare method*.
. In *Compare as*, choose the type of comparison: text, binary, image or web page.
  *Automatic* chooses the type for you (see <<compare-types>>).
. Click *Compare*.

TIP: To compare text that is not in a file, choose *File → New text compare* (kbd:[Ctrl+N]).
This opens two empty sides.
Paste text with kbd:[Ctrl+V], or double-click a line to type.

[[compare-types]]
=== Comparison types

OxideMerge has five types of comparison:

[cols="1,4"]
|===
|Type |What it shows

|Text
|Lines side by side, with the changed words highlighted.
You can edit and merge the text.
Comparison options and compare rules decide which changes count as differences.
Use it for source code, configuration files, CSV files and any other readable text.

|Binary
|The bytes in a hexadecimal view.
You can copy and save differences, but the lines are not aligned.
For example, one byte inserted near the start moves all the bytes after it.

|Image
|The pixels: side by side, as an overlay, with a swipe divider, blinking, or as a difference image.
You can copy regions that are different from one image to the other.

|Folder
|The items of two or three folders.
You can copy, delete and merge items, and open each file in its own comparison.

|Web page
|Two or three web pages: as visible text, as formatted Markdown, as screenshots, as HTML source or
as downloaded resources.
Web pages are read-only. OxideMerge never saves anything to a web server.
|===

When *Compare as* is *Automatic*, OxideMerge checks these conditions in this order and uses the
first one that matches:

. Any side is an `http://` or `https://` address: web page comparison.
. Every side is an HTML file (`.html` or `.htm`): web page comparison.
  It uses the Formatted mode, unless you chose another mode before.
  Exception: a merge with an output file (`-o`) or a console patch (`--patch`) compares the files
  as text.
. Every side is a folder: folder comparison.
. Every side is an archive: the archives are extracted and compared as folders.
. Every file has an image extension, such as `.png`, `.jpg`, `.gif`, `.bmp`, `.tif` or `.webp`:
  image comparison.
. A file has a zero byte in its first 8 KB: binary comparison.
  Exceptions: an unpacker plugin can convert the file to text (see <<unpackers>>), and UTF-16
  text with a byte order mark is still text.
. Anything else: text comparison.

To choose the type yourself, use *Compare as* in the dialog, *Compare → Compare as* in an open
tab, or `-t` on the command line.

== Comparing text files

.A two-way text comparison
image::text.png[Text comparison]

=== The text comparison window

Each side has a header and a footer:

* The header shows the file name and its folder.
  The lock button makes the side read-only.
* The footer shows the line-ending style and the encoding that OxideMerge uses when it saves the
  file. It also shows the current line and the number of lines.

If you choose another encoding in the footer, OxideMerge reads the file again with that encoding.
Check the text after you change the encoding, especially before you edit or save.

Colors show the differences:

* Changed lines are blue.
* In a two-way comparison, lines that are on one side only are green.
* In a three-way comparison, conflicts that are not resolved are red.
* Inside a changed line, the changed words or characters are highlighted.

If you turn on *Color-blind friendly diff colors* in *Options → General*, changed lines are purple
and lines on one side only are blue.

Between the panes, a connector joins the two sides of each difference.
The current difference is highlighted.
Its copy arrows appear when the difference is current or when the pointer is over it.

The toolbar has four groups of buttons:

* *Differences*: go to the next, previous, first or last difference.
* *Copy* (*Merge* in a three-way comparison): copy differences between the sides.
* *Edit*: undo and redo.
* *View*: find, collapse unchanged lines and word wrap.

In a wide window, the toolbar shows the group names.
The +/− numbers next to the difference number are the numbers of added and removed lines.

The location pane, at the right, shows an overview of the whole file.
Click in it to go to that place.
Binary comparisons and the Formatted mode of web page comparisons have a location pane too.

=== Moving between differences

[cols="1,2"]
|===
|Keys |Action

|kbd:[Alt+↓], kbd:[Alt+↑]
|Go to the next or previous difference

|kbd:[Alt+Home], kbd:[Alt+End]
|Go to the first or last difference

|kbd:[Alt+PgDn], kbd:[Alt+PgUp]
|Go to the next or previous conflict (three-way comparison)

|kbd:[Ctrl+G]
|Go to a line number
|===

If you opened the file from a folder comparison, you can continue to other files.
After the last difference, kbd:[Alt+↓] opens the next file that has differences.
Before the first difference, kbd:[Alt+↑] opens the previous one, at its last difference.
In a three-way folder comparison, kbd:[Alt+PgDn] and kbd:[Alt+PgUp] go on in the same way to the
next or previous file that still has an open conflict.

Hold the pointer over a navigation button to see what it goes through, its keys, and that it
stops at the end instead of starting again at the top.

[[folder-navigation]]
==== Moving through the differences of a folder

In a folder comparison, the same keys work on the file shown below the folder list, and on the
other files of the folder:

* kbd:[Alt+↓] goes to the next difference of the file. After its last difference, it selects the
  next file that has differences and goes to its first difference.
* kbd:[Alt+↑] goes the other way: before the first difference, it goes to the last difference of
  the previous file.
* kbd:[Alt+Home] and kbd:[Alt+End] go to the first difference of the first file and the last
  difference of the last file.
* The status bar shows where you are, for example _File 2 / 5 · Difference 3 / 7_.

The files are the ones that the folder list shows as different, in the order of the list.
Binary files are included. Files that could not be read are not.
At the last difference of the last file, OxideMerge says so; it does not start again at the top.

If you press a key while a file is still loading, OxideMerge remembers it and moves when the file
is shown, so no difference is skipped. If a file cannot be read, the pane says so and offers
*Retry* and *Skip*. While the folders are still being compared, more files may follow: the
message says so instead of ending. If the comparison was stopped, the message at the end says
that it covers only the files compared.

A file that changed after the comparison is shown as it is now. If it no longer has differences,
the next step goes on to the next file. A file shown below the list that changes on disk is
loaded again at the same difference.

In a three-way folder comparison, kbd:[Alt+PgDn] and kbd:[Alt+PgUp] go through the open conflicts
of the files that both sides changed. A file whose changes merge without conflicts is passed over
once it is loaded, and a file changed on one side only is not visited. kbd:[Alt+↓] still stops at
every changed file.

=== Copying differences

When you copy a difference, OxideMerge changes the text in the destination pane.
The file on disk changes only when you save it.
Before you copy, check which pane is active and which way the arrow points.

* Click an arrow on the divider between the panes to copy the current difference, or the
  difference under the pointer.
* kbd:[Alt+→] and kbd:[Alt+←] copy the current difference, or the selected lines, to the right or
  to the left.
* kbd:[Ctrl+Alt+→] and kbd:[Ctrl+Alt+←] copy all differences to the right or to the left.
* kbd:[Ctrl+Z] undoes a change. kbd:[Ctrl+Y] or kbd:[Ctrl+Shift+Z] redoes it.

=== Saving files

* kbd:[Ctrl+S] saves all changed panes in the current tab.
* kbd:[Ctrl+Shift+S] saves all changed panes in all tabs.
* *File → Save as* saves one side with another name.

OxideMerge saves a file safely:

. It writes the new content to a temporary file in the same folder.
. It replaces the original file with the temporary file.

If one of these steps fails, OxideMerge shows an error. It never writes directly over the original.
For this reason, the folder must allow OxideMerge to create and replace files, even when the file
itself is writable.

To keep the previous content of a file, turn on *Keep a .bak copy when saving over a file* in
*Options → General*.
OxideMerge then keeps the old content as `<name>.bak`.
The next save replaces this backup, so it is not a version history.

=== Editing text

You can edit each pane that is not read-only. Editing is line-based.

* To edit a line, double-click it, or press kbd:[F2] or kbd:[Enter].
* To select lines, drag over them, kbd:[Shift]+click, or press kbd:[Shift+↑] and kbd:[Shift+↓].
* kbd:[Ctrl+C] copies the selected lines.
  kbd:[Ctrl+V] pastes below the current line, or replaces the selected lines.
* kbd:[Ctrl+\]] indents the selected lines, and kbd:[Ctrl+[] unindents them.

Right-click a line to edit it, insert a line below it, delete it, copy its text, set a bookmark,
or create a compare rule from it (see <<add-rule>>).

Edit markers in the gutter show the lines that changed since you opened the files.

When another program changes a file, OxideMerge notices it when its window becomes active again:

* A file without unsaved changes reloads automatically.
* A file with unsaved changes shows a message with a reload option.
  Reloading replaces your edits with the file on disk.

=== Find and replace

* kbd:[Ctrl+F] opens the find bar.
  kbd:[F3] and kbd:[Shift+F3] find the next and the previous match. kbd:[Esc] closes the bar.
* kbd:[Ctrl+H] (kbd:[Cmd+Alt+F] on macOS) opens find and replace.
* The search options are *Match case*, *Whole word* and *Regular expression*.
  With a regular expression, `$1` in the replacement text means the first captured group.
* You can undo *Replace all* in one step.

=== Bookmarks

* kbd:[Ctrl+F2] sets or removes a bookmark on the current line.
* kbd:[F4] and kbd:[Shift+F4] go to the next and the previous bookmark.
* *Edit → Bookmarks → Bookmark comment...* adds a comment to a bookmark.
  The comment appears when you move the pointer over the gutter, and in HTML reports.
* *Edit → Bookmarks → Clear bookmarks* removes all bookmarks.

Bookmarks are marked in the gutter and in the location pane.

[[sync-points]]
=== Synchronization points

Sometimes the comparison pairs the wrong lines.
For example, this can happen when a function was rewritten and moved.
Use a synchronization point to tell OxideMerge which lines belong together:

. Put the cursor on a line on one side.
  Then choose *Merge → Set synchronization point* (kbd:[Alt+S]), or right-click the line.
. Do the same on the matching line on the other side.
  In a three-way comparison, do it on the third side too.

OxideMerge shows these lines on the same row.
It compares the text before them and the text after them separately.

* You can add as many points as you need.
  OxideMerge refuses a point that would cross another point.
* Synchronization points are marked in the gutter.
  They stay with their lines when you edit, undo or reload, and they are kept in saved
  comparisons.
* To cancel a line that you picked, run the command again on that line.
* To remove a point, run the command again on one of its lines.
* To remove all points, choose *Merge → Clear synchronization points*.

=== View options

*View → Text compare* has these options:

* *Location pane* and *Line detail pane*.
  The line detail pane shows the current line of each side, one above the other, with word wrap.
  Use it to find small differences in long lines.
* *Line numbers*, *Edit markers*, *View whitespace* and *Syntax highlighting*.
* *Collapse unchanged lines* (kbd:[Alt+C]) hides unchanged lines behind a bar.
  Three lines stay visible around each difference. Click the bar to show the hidden lines.
* *Word wrap* (kbd:[Alt+Z]).

*View → Zoom* (kbd:[Ctrl+{plus}], kbd:[Ctrl+-] and kbd:[Ctrl+0]) changes the text size.

*Text layout* is in *View → Text compare* and in *Options → General*:

Compact rows:: The default. Each side shows its own lines, without empty space.
Aligned rows:: Empty space is added opposite inserted and deleted lines, so the lines after them
stay side by side.

The layout applies to all open two-way and three-way text comparisons, and is saved for the next
session. It does not change the files or the compare rules.

[[inline-view]]
==== Inline view

In a two-way comparison, the *Inline view* button next to *Word wrap* shows the differences in one
column. The command palette has the same command.

.The inline view
image::inline.png[Inline view]

* Removed lines come first, then the lines that replace them.
  Each line shows its old and its new line number.
* When *Collapse unchanged lines* is on, unchanged lines are hidden. Click a fold to show them.
* You can move between differences and copy them as usual.
  The arrow keys move from line to line, and kbd:[Ctrl+C] copies the current line.
* To edit or select lines, go back to the side-by-side view.

=== CSV and TSV files

For CSV and TSV files, the toolbar has a *Table view*.
It compares records, not lines, so a quoted field can contain line breaks.

.The table view of two CSV files
image::csv.png[Table view]

* Drag a column border to change its width.
* To edit a cell, double-click it, or right-click it and choose *Edit cell*.
  You can also select it and press kbd:[F2] or kbd:[Enter].
  A cell can contain several lines.
* To copy one field to the matching record on another side, right-click the cell and choose
  *Copy cell*. Both records must have that column.
* The arrow keys move between records and columns.
  kbd:[PgUp] and kbd:[PgDn] move through records, and kbd:[Ctrl+Home] and kbd:[Ctrl+End] select
  the first and the last record.
* *Go to line* uses the line numbers of the file.

When you edit a cell, OxideMerge keeps the quotes and line endings outside that field, and you can
undo and redo the change.
You cannot edit converted or read-only documents.

When you copy a difference in the table view, only its selected lines change.
If this would break the CSV quoting, OxideMerge refuses the copy and does not change the document.
In this case, copy cells or use the text view.
If a quoted record is not valid, the table shows an error; switch to the text view to correct it.

[[table-keys]]
==== Matching rows by key

By default, the table view pairs records by their position, like lines. When records are
sorted differently, or some are added or removed, pair them by a key instead.
In a two-way comparison, the bar above the table has these settings:

*Match rows by*:: *Position* (the default) or *Key columns*.
*Keys*:: The columns that identify a record, such as `id`. Choose one or more.
*First row is header*:: Use the first row for column names. It is not compared.
*Columns by*:: Pair columns by *Position* or by *Header name*, so that reordered columns still match.
*Ignore row order*:: A record that only moved is not a difference: next and previous difference
skip it, but it keeps its `↕` mark.
*Numeric tolerance*:: Numbers this close count as equal. `0.01` is a difference, `1%` a
fraction of the larger number. Leave it empty to compare exactly.
*Rows in*:: *Left order* (the default) lists the rows as the left table has them, with records
only on the right after the record before them. *Right order* follows the right table.
*Key order* sorts by key: numbers by value, before text, and rows without a key last.

The summary shows how many records were added, removed, modified, reordered and ambiguous.
The row markers are `+` added, `−` removed, `~` modified, `↕` moved and `?` ambiguous.

* Next and previous difference go through the records that differ.
* *Copy cell* copies into the paired column of the matching record.
  Copying a whole record replaces the cells of the matching record, or adds or removes it.
* A key that is empty, or used by more than one record, is _ambiguous_.
  Ambiguous records are never copied. *Next ambiguous row* finds them.
* If a key column is missing on one side, OxideMerge matches by position and says why.

Tables with more than 100,000 records on both sides together are matched in the background. The
bar shows how many records are done, with *Cancel*. After a cancel, the rows are matched by
position, and *Match by key* starts again.

HTML and XML reports of a table matched by key say how the rows were matched: the keys, the
header row, how columns were paired, the row order, the tolerance, the counts and the warnings.
XML reports hold them in a `<table-match>` element.

The settings are saved in projects. Older projects open with matching by position.

[[git-revision]]
=== Comparing with a Git revision

*File → Compare with Git revision...* compares a file or folder with an earlier version from Git.
The version can be `HEAD`, a branch, a tag or a commit. The dialog lists recent commits.

The Git version is shown read-only on the left. The current file or folder is on the right.
Git must be installed and in your `PATH`, and the path must be in a Git repository.

On the command line, use `--git-rev`:

[source,sh]
----
oxidemerge --git-rev HEAD~1 src/main.rs
----

[[merging]]
== Merging files and resolving conflicts

[[three-way-merge]]
=== Three-way merge

.A three-way comparison
image::three.png[Three-way text comparison]

A three-way merge combines two edited versions of a file.
Open the files in this order: your version, the base, the other version.
OxideMerge compares the left and right versions with the base, and combines the changes in the
middle pane.

==== Step 1: Choose the output file

By default, saving the middle pane overwrites the base file.
To keep the base file, give a separate output file when you start:

[source,sh]
----
oxidemerge mine.txt base.txt theirs.txt -o merged.txt
----

The middle pane starts with the content of the base file.
When you save, OxideMerge writes the result to `merged.txt`.
You can also choose *File → Save as* to save the result in another file.

Make the left and right panes read-only if you only use them as sources.

==== Step 2: Merge and resolve conflicts

The merge bar above the panes shows how many conflicts are left.
It has these buttons:

* *Next conflict*.
* *Take left*, *Take both* and *Take right*, for the current conflict.
* *Mark resolved*, for a conflict that you edited by hand.
  It keeps the middle text as it is and counts the conflict as resolved.
* *Save result*, at the right end, saves the middle pane.
  It becomes the main button when no conflicts are left.

To merge:

. Choose *Merge → Auto merge*.
  This copies two kinds of changes to the middle pane: changes made on one side only, and the same
  change made on both sides.
. Go to each remaining conflict with kbd:[Alt+PgDn] and kbd:[Alt+PgUp].
. Copy the change that you need from the left or the right, or edit the middle pane.
. To keep both changes, right-click the difference and choose *Take left, then right* or
  *Take right, then left*.
  Then check the result for repeated or conflicting text.
. Save the result. Check that the destination path is correct.

IMPORTANT: Auto merge works only on the text. It does not check that the result is correct.
Review the result, and run the checks that your project needs, before you use it.

[[conflict-files]]
=== Resolving conflict files

.A conflict file in the three-way view
image::conflict.png[Conflict file]

A conflict file is a file with version-control conflict markers:
`<<<<<<<`, `|||||||`, `=======` and `>>>>>>>`.
OxideMerge opens it in the three-way view.

To open a conflict file, use one of these:

* *File → Open conflict file...*.
* *Open conflict file* on the start page.
* The command line: `oxidemerge conflict.txt`.

The left side is *Mine*, the right side is *Theirs*, and the middle is the *Merged result*.
Resolve each conflict, then save the middle pane.
OxideMerge writes the result back to the conflict file.

NOTE: This is different from opening three separate files.
For a conflict file, the original file is the output.

[[folder-comparison]]
== Comparing folders

.A folder comparison
image::folder.png[Folder comparison]

A folder comparison lists the items of two or three folders and the result for each item.
Results appear while the comparison runs: OxideMerge compares the files during the folder scan
and lists each difference as soon as it finds it.
If a long comparison finishes while the window is in the background, OxideMerge asks for your
attention.

=== The folder list

Each row shows these columns:

* *Name*.
* *Folder*: the folder that contains the item. This column is shown in a flat list only.
* *Comparison result*.
* *Modified*: the newest date of all sides.
  If the dates are different, the newer side is named after the date.
  Move the pointer over the date to see the date of each side.
* The size on each side.
* *Extension*.

Click a column header to sort by that column. Click it again to reverse the order.
A colored bar at the left edge of a row marks a difference or an item that is on one side only.

The comparison result is one of these:

[cols="1,2"]
|===
|Result |Meaning

|*Identical*, *Different*
|The files are the same or not the same. *Binary* marks binary files.

|For example, *3 different · 1 only in Left*
|A folder that is different. The text tells what is different inside it.

|*Left only*, *Middle only*, *Right only*
|The item is on one side only.

|*Left is different*, *Middle is different*, *Right is different*
|Three-way comparison: one side is different from the other two.

|*Missing in Left*, *Missing in Middle*, *Missing in Right*
|Three-way comparison: the item is on the other two sides only.

|*Error*
|OxideMerge could not read the item.
|===

Move the pointer over a result to see the full description, for example *Text files are
different*.

The chips under the paths count the items: *All*, *Different*, *Only in Left*, *Only in Right*,
*Only in Middle* (three-way only) and *Identical*.
Click a chip to hide or show that kind of item.
Some details about the counts:

* In a three-way comparison, an item that is missing from one side counts as different.
* Empty folders, and folders that were not scanned, count by the result that they show.
* If *Include subfolders* is off, the subfolders are not compared.
  They count only in *All*, and no chip hides them.

The status bar shows how long the comparison took.

=== Display options

*View → Folder list* has these options:

Tree mode:: Shows subfolders as a tree. Turn it off for a flat list.
kbd:[→] and kbd:[←] expand and collapse a folder.
The toolbar has *Expand all* and *Collapse all*.
Show:: Hides or shows *Identical*, *Different*, *Left only*, *Middle only* and *Right only* items.
File compare below the folder list:: Shows the differences of the selected file under the list,
without opening a tab.
The pane button on the toolbar, or kbd:[Alt+P], shows or hides this pane.

.The file compare below the folder list
image::docked.png[Folder comparison with the file compare pane]

The navigation keys work differently when this pane is shown:

[cols="1,2,2"]
|===
|Keys |With the file compare pane |Without the pane

|kbd:[Alt+↓], kbd:[Alt+↑]
|Go to the next or previous difference in the file.
After the last difference, go on to the next file that has differences.
|Select the next or previous file that has differences.

|kbd:[Alt+Home], kbd:[Alt+End]
|Go to the first or last difference in the file.
|Select the first or last file that has differences.
|===

The arrow buttons of the pane do the same as kbd:[Alt+↓] and kbd:[Alt+↑].
If you press a key while a file is still loading, OxideMerge waits for the file, so no difference
is skipped.
If a review filter is active, these keys go only through the files that the filter lists.

=== The toolbar

From left to right:

* *Refresh* (kbd:[F5]) compares the folders again.
* *Expand all* and *Collapse all*, in tree mode.
* *File compare below the folder list* (kbd:[Alt+P]) shows or hides the file compare pane.
* *Copy to right* and *Copy to left* copy the selected items.

* *Find by name* (kbd:[Ctrl+F]) shows only the items whose names contain the text you type.

In a narrow window, *All differences* and *Export HTML* become icons, and the chips show only

[[compare-methods]]
=== Comparison methods

[cols="1,3"]
|===
|Method |How files are compared

|Full contents
|Text files are compared line by line, with the comparison options and compare rules.
Files that differ only in ignored ways count as identical.

|Quick contents
|The bytes are compared.
Files of different sizes are found without reading them.

|Binary contents
|The bytes are compared, as in *Quick contents*. The result is marked as binary.

|Modified date
|The modification dates are compared.
The *Date tolerance (seconds)* in *Options → Folder* sets how far apart two dates can be.

|Modified date and size
|The dates and the sizes must both match.

|Size
|Only the sizes are compared.
|===

Which method to use:

* Use *Full contents* when compare rules and ignored differences matter.
* Use *Quick contents* or *Binary contents* to check that files are exactly the same.
* Use a date or size method for a fast first check.
  Note that the same date and size do not prove that the contents are the same.

The byte methods read files in small parts, so large files do not have to fit in memory.
A full text comparison can still load changed files into memory.

=== Selecting and opening items

Select items with the mouse or the keyboard:

* The arrow keys, kbd:[PgUp], kbd:[PgDn], kbd:[Home] and kbd:[End] move the selection.
  Hold kbd:[Shift] to extend it.
* kbd:[Ctrl]+click adds an item to the selection, or removes it.
* kbd:[Ctrl+A] selects all items.

To open items:

* Double-click an item, or press kbd:[Enter], to compare it in its own tab.
  In tree mode, this expands or collapses a folder instead.
  To open a folder in its own folder comparison, use a flat list, or right-click the folder and
  choose *Compare*.
* Press kbd:[Space] for a *Quick preview*: a colored view of the differences of the selected file,
  without a new tab.
  In the preview, kbd:[↑] and kbd:[↓] go to the next item, kbd:[Enter] opens the item, and
  kbd:[Space] or kbd:[Esc] closes the preview.

=== Copying and deleting items

* kbd:[Alt+→] and kbd:[Alt+←] copy the selected items to the right or to the left.
* Right-click an item for more commands:
** *Copy* to another side.
** *Copy to folder...*: copies the selected items of one side to another folder, and keeps their
   relative paths.
** *Delete* from a side.
** *Open with associated application*.
** *Show in file manager*.
** *Copy full path*.
** *Select by name...*.

These settings in *Options → General* control file operations:

* *Confirm copy operations*: OxideMerge asks before it copies items.
  It always asks before it deletes items.
* *Use the recycle bin when deleting*: deleted items go to the recycle bin or trash.
  If an item cannot go there, OxideMerge does not delete it.
* *Keep a .bak copy when saving over a file*: OxideMerge keeps the old content of a replaced file.

IMPORTANT: Copy and delete change the files on disk at once.
They do not wait for *Save*, and the *Undo* command of the text editor does not reverse them.
Check the selected items and the destination first.

=== Reviewing all differences

.All differences

*All differences* shows all changed text files of a folder comparison in one tab.
Click it on the folder comparison toolbar, or choose *Compare → All differences*.
The filter and the *Show* settings of the folder comparison apply.

* The list on the left shows each file and its number of differences.
  *Filter files…* (kbd:[Ctrl+F]) shortens the list. Click a file to scroll to it.
* Each file is a card that shows its differences side by side.

[[folder-merge]]
=== Merging folders automatically

In a three-way folder comparison, the middle folder is the base.
*Merge → Auto merge folders...* brings the changes from both sides into the middle folder:

* An item that was changed, added or removed on one side only is copied or removed.
* A change that is the same on both sides is applied once.
* A text file that was changed on both sides is merged line by line, if the changes do not
  overlap.

==== Before you start

. In *Options → Folder*, turn on *Include subfolders* and *Include contents of unique subfolders*.
. Let the comparison finish.

IMPORTANT: The merge writes the result into the middle folder.
To keep the original base folder, use a copy of it as the middle folder.

==== Review the plan

OxideMerge first shows a plan: the items that it will copy, delete and merge, and the conflicts
that it cannot resolve. Review the plan before you confirm it.

OxideMerge does not change these files: files with edits that conflict, files with content that
it cannot merge, symbolic links, and files that it cannot read.
If a file changed after the comparison, refresh the comparison and try again.

==== How the merge protects your files

The merge is all or nothing: either every change is made, or the middle folder stays as it was.

* _Before the merge_, OxideMerge checks every item.
  Nothing is merged if an item changed after the plan was made, if an item would be written
  outside the middle folder, or if a backup file would replace a compared file.
  OxideMerge lists these items.
* _During the merge_, OxideMerge checks each file again just before it writes it.
  If another program changes a file, the merge stops.
  You can also click *Stop* to stop the merge.
* _When the merge stops or fails_, for example because a folder is read-only or the disk is full,
  OxideMerge undoes all changes made so far.
  The middle folder is then as it was, and removed folders get back their permissions.
  A file that the merge moved to the trash is restored from a copy, so the trash keeps a copy too.

To make the undo possible, OxideMerge keeps copies of the original files in a
`.oxidemerge-undo-…` folder at the top of the middle folder.
If it cannot create this folder there, it uses the system's temporary folder.
Folder comparisons do not list this folder.
A deleted file is only moved to this folder, and is moved back if the merge is undone.

If OxideMerge cannot put a file back, it keeps the undo folder and shows where it is.
The `index.txt` file in that folder lists the original path of each copy, so you can restore the
files by hand.

[[folder-sync]]
=== Synchronizing two folders

In a two-way folder comparison, *Synchronize folders...* (on the toolbar and in the *Merge* menu)
makes one folder, the _destination_, match the other, the _source_. You see the plan first.
Nothing changes until you apply it.

==== Modes

*Mirror left → right*, *Mirror right → left*::
The destination ends up with the files of the source. New and changed files are copied, and
files and folders that only the destination has are deleted.
*Update right from left*, *Update left from right*::
New and changed files are copied. Nothing is deleted.

A read-only side, such as a Git revision, cannot be the destination.
OxideMerge decides by the contents (SHA-256), never by a newer modification time alone.
Files that compared identical but differ in size or time are read to be sure.

==== Before you start

. Turn on *Include subfolders* and *Include contents of unique subfolders* in *Options → Folder*.
. Let the comparison finish. A stopped comparison cannot be synchronized.

The two folders must be different folders, and neither may be inside the other.

==== The preview

The preview is read-only. It lists each item with its action and the reason:

[cols="1,3"]
|===
|Action |Meaning

|Create folder, Copy
|The item is only in the source.

|Replace
|The contents differ. The destination file is overwritten.

|Delete, Remove folder
|The item is only in the destination (mirror only). A folder is removed only when it is empty
afterwards.

|Skip
|The item is only in the destination, and the mode is update.

|Conflict
|OxideMerge leaves the item alone because it is not safe to decide.
|===

Conflicts are items that cannot be read, symbolic links (never followed or copied), devices,
a file on one side and a folder on the other, names that differ from another only in letter case
or in how accents on Latin letters are written (composed or not), and items that changed after
the comparison.

Click an item for its details: the size and the start of the SHA-256 on each side, and whether
the action adds to, or overwrites and deletes in, the destination.

A copy whose contents match a file that the plan deletes is a file renamed or moved in the
source. *Rename* lists such pairs as _old name → new name_, and the copy and the deletion show the
other name too. They are still applied as a copy and a deletion.

Warnings appear above the list:

* When a filter or the hidden-file setting left items out, a mirror does not delete them,
  so the destination may not be an exact mirror. A folder that still holds such items is kept.
* Large deletions are flagged and ask for a second confirmation.

*Export plan...* saves the plan as JSON, with a version number and paths relative to the folders.
It does not contain the folders' absolute paths. It records the filter, and a SHA-256 of the two
folder paths, so a plan is applied only to the folders it was made for.

==== Applying the plan

*Apply changes...* asks for confirmation and names the destination. When many items would be
deleted, you must also tick a box that states their number.

OxideMerge then works in this order: it creates folders, copies and replaces files, deletes files
and finally removes empty folders. The dialog shows the count and the item being changed. For each item it first checks that the source and the
destination are still as in the preview. Every file is copied to a temporary file next to its
destination, checked against the planned SHA-256 and then renamed into place. At the end, all
copied files are checked again.

If a file changed after the preview, even with the same size and modification time, nothing is
applied, and the file is named.

==== If something goes wrong

Before it replaces or deletes a file, OxideMerge copies it into a recovery journal in the
`sync-recovery` folder of the settings folder, never inside the synchronized folders.

* If a change fails, or you click *Stop*, OxideMerge undoes the changes made so far, last first.
* If a file was changed again meanwhile, OxideMerge does not overwrite it. It reports
  _Partially applied — recovery required_ and keeps the journal with the copies.
* If OxideMerge ends before the synchronization finishes, the next start offers to undo it or
  to keep the folders as they are. Until then, these folders cannot be synchronized again.

IMPORTANT: Applying is not one atomic step for several files. Each file is replaced atomically,
but another program can see some files already changed. The trash is not used.

[[archives]]
=== Archives

OxideMerge extracts archives and compares them as folders. It supports these formats:

* ZIP-based formats: `.zip`, `.jar`, `.apk`, `.docx`, `.xlsx`, `.odt`, `.epub`, `.nupkg` and
  more.
* `.tar`, `.tar.gz` / `.tgz`, `.tar.bz2` / `.tbz2` and `.tar.xz` / `.txz`.
* `.7z`.

The extracted files are read-only. OxideMerge never writes changes back into an archive.
It refuses archives that would extract to more than 8 GB or more than 500,000 files.
RAR is not supported.

[[binary-comparison]]
== Comparing binary files

.A binary comparison
image::binary.png[Binary comparison]

Binary files open in a hexadecimal view, side by side.
Bytes that are different are highlighted, and the sides scroll together.

* kbd:[Alt+↓] and kbd:[Alt+↑] go to the next and the previous difference.
* kbd:[Ctrl+F] finds hexadecimal bytes, such as `DE AD BE EF`, or text.
* kbd:[Ctrl+G] goes to an offset. Write it as `0x1F00`, `1F00h` or a decimal number.
* You can copy differences to the other side and save them, as in a text comparison.

To change the number of bytes on each line, use *Bytes per line (binary)* in
*Options → Image / Binary / Web*.

=== Editing bytes

. Click a byte on the side that you want to change.
  Click in the hexadecimal column to type hexadecimal digits, or in the text column on the right
  to type characters.
. Type the new value.
  In the hexadecimal column, two digits make one byte: the first digit changes the first half of
  the byte, and the second digit changes the second half.
  In the text column, each character replaces one byte. Only ASCII characters can be typed.
. Save with kbd:[Ctrl+S].

By default, typing replaces the bytes at the cursor. To insert bytes instead, press kbd:[Insert]
or click *Insert* on the toolbar. Typing after the last byte always adds bytes.

* The arrow keys, kbd:[PgUp], kbd:[PgDn], kbd:[Home] and kbd:[End] move the cursor.
  kbd:[Ctrl+Home] and kbd:[Ctrl+End] go to the start and the end of the file.
* kbd:[Delete] deletes the byte at the cursor. kbd:[Backspace] deletes the byte before it.
* Paste (kbd:[Ctrl+V]) in the hexadecimal column writes hexadecimal bytes such as `DE AD BE EF`.
  Other text is refused there. In the text column, the text is written as it is.
* kbd:[Ctrl+Z] undoes the typing since you last moved the cursor, or a paste.

Sides that are read-only cannot be changed. Click the lock icon above a side to change this.

To compare another kind of file as a web page, choose *Compare as → Web page*, or use `-t web` on

Choose a mode in the selector at the top of the tab. OxideMerge remembers the last mode you used.

[cols="1,3"]

|Mode |What is compared

|Text
|The text of each page, in the text comparison.

The cells of a table row are on one line, separated by tabs.

|Formatted

[[web-formatted]]
=== The Formatted mode

The Formatted mode keeps the look of headings, paragraphs, emphasis, links, lists, quotes, code
blocks and tables. Images are shown as links.

.Two web pages in the Formatted mode
image::web.png[Web page comparison in the Formatted mode]

OxideMerge compares the pages block by block.
A block is a heading, a paragraph, a list item, a table, a quote or a code block.

* Blocks that are different are highlighted.
  Each one is placed opposite the changed block of the same kind on the other pages.
* A block that is on one page only is placed opposite an empty space.
* Inside a changed block, the changed words or characters have a stronger highlight.
  The *Inline differences* option controls this, as in the text comparison.
* Tables have lines around their cells, and their rows are aligned.
  In a row that is different, the changed words are highlighted.
  If a row or a column is missing on the other page, its cells are highlighted completely.
* Each changed block is a separate difference, even when it follows another changed block.

To move between differences, use the buttons above the pages, or the same keys as in the text
comparison.

* The current difference has a stronger highlight.
  The blocks that are compared have an outline on every page.
  The outline is strongest on the page that you clicked last.
* Click a block to make it the current block.
  The next and previous differences are then found from that block.
* The pages scroll only when the difference is not visible.
  The difference is then shown about one third from the top.

The location pane, at the right of the pages, shows all differences.
The current difference is in the accent color, and the visible part of the page has an outline.
Click or drag in the location pane to go to that place.
To show or hide it, choose *View → Text compare → Location pane*.

[[web-screenshots]]
=== The screenshot modes

The Full page and Screenshot (visible area) modes show screenshots in the image view.

When *Highlight differences* is on, OxideMerge highlights the text that is different on the page
itself, before it takes the screenshot:

* Changed blocks are yellow.
* Changed words inside them are orange.

This is like *View Differences* in WinMerge.
Because OxideMerge compares the text, not the pixels, a change that moves the rest of the page down
does not mark everything below it.
Pages that are taller than 16384 pixels are cut.

=== How pages are loaded

The Text, HTML source, Formatted and Resource tree modes use the HTML as the server sends it, or as
the file is saved.
They do not need a browser, so they open quickly.
The scripts of the page do not run, so content that scripts add is missing.
To see that content, use a screenshot mode.

The Text and Formatted modes leave out content that the page hides: elements with `hidden`,
`aria-hidden="true"`, or an inline `display: none` or `visibility: hidden` style.
Content that only a style sheet hides is still compared.

The screenshot modes use a Chromium-based browser. OxideMerge finds Edge, Chrome, Chromium and
Brave automatically.
The browser runs without a window.
It runs the scripts of each page, so the screenshots show each page as it looks in a browser.

* All pages load at the same time, each in its own browser tab.
* After 45 seconds, OxideMerge uses each page as it is at that moment.
* Dialogs that a page opens, such as `alert`, are closed automatically.
* If a page redirects after it loads, OxideMerge uses the page that it redirects to.
* On macOS and Linux, OxideMerge talks to the browser through a private pipe.
  On Windows, it uses a network port that only this computer can reach.
  The port is open only while the pages load.
* If the browser cannot load a page (the page cannot be reached, does not load in time, or its tab
  crashes), that page is blank and its pane header shows the error.
  The other pages are still compared.

OxideMerge decodes pages the same way as browsers.
It uses the first of these that it finds: a byte order mark, the charset in the HTTP
`Content-Type` header, a `<meta>` charset, or a guess from the content.

* If the server returns a status code that is not 2xx, the pane header shows it, and the page that
  came with it is compared.
* OxideMerge reports a page, with its address, if the page cannot be reached, takes more than 30
  seconds, sends a response that is not valid, or is larger than 50 MB.

=== Resource tree limits

The Resource tree mode downloads only the resources that each page names itself.
It does not follow links inside style sheets or scripts.

* Each page can have at most 400 resources, and each resource can be at most 20 MB.
* Resources that cannot be downloaded are counted in the status bar. The other resources are still
  compared.
* For your safety, a web page cannot load local files.
  Only a page on this computer or on a private network (such as `localhost` or `192.168.x.x`)
  can load resources from such an address, or redirect to one.
  Other resources of this kind are skipped and counted in the status bar.
* The addresses that you enter yourself are always loaded.

These limits do not apply to the screenshot modes: the browser loads everything that a page asks
for.

=== Web page settings

These settings are in *Options → Image / Binary / Web*:

* *Browser used to render pages*: the browser for the screenshot modes.
  Leave it empty to find a supported browser automatically.
* *Screenshot width* and *Screenshot height*: the size of the browser window.

The console comparison (`--cli` with HTML files, or with `-t web`) uses the last mode that you
chose in the window. It does not use a browser:

* Formatted (the default) compares the Markdown of the pages line by line.
* HTML source compares the HTML.
* The other modes compare the visible text.

NOTE: Only the screenshot modes run the scripts of the page.
Logins are not supported, so a page that needs a login can show its login page.
No mode saves changes to a web server.

[[differences-shown]]
== Controlling which differences are shown

Three kinds of settings decide what OxideMerge shows as a difference:

* Filters select which files and folders a folder comparison includes.
* Comparison options decide which text changes count, for example whitespace or case.
* Compare rules ignore or replace text that matches patterns.

These settings change the comparison result only. They never change the files.

TIP: If a change that you expect is not shown, check these settings before you decide that the
files are identical.

[[compare-options]]
=== Comparison options

*Compare → Compare options* has the most common options.
*Options → Compare* has all of them:

Whitespace::
*Compare*: whitespace counts.
*Ignore changes*: a different amount of whitespace does not count.
*Ignore all*: whitespace does not count at all.
Ignore blank lines:: Extra blank lines do not count.
Ignore case:: Uppercase and lowercase letters are the same.
Ignore carriage return differences (Windows/Unix/Mac):: The line endings `CRLF`, `LF` and `CR`
are the same.
Ignore numbers:: Digits are ignored.
Ignore code page differences:: Files in different encodings that have the same text are the
same.
Ignore comment changes:: Changes inside comments do not count.
This works for languages whose comment syntax is known: C-like languages, scripts, SQL, HTML,
XML, CSS, Lua, Haskell and more.
Format JSON and XML before comparing:: JSON and XML are indented again, and JSON keys are sorted,
so that layout changes do not count.
The formatted view is read-only. Turn this option off to edit or merge the files.
Detect moved lines:: Blocks of lines that moved are shown as moved.
Diff algorithm:: *Myers*, *Patience* or *LCS*.
Inline differences:: How changes inside a line are highlighted: *Off*, *Word level* or
*Character level*.
Treat numbers as equal within:: Numbers that are at most this far apart, for example `0.001`, are
the same. This is useful for measurements and generated data.

In folder comparisons, these options apply to text files when the method is *Full contents*.
The other methods do not use them.

[[compare-rules]]
=== Compare rules

A compare rules file (`.oxrules`) contains rules of three kinds:

Ignore lines matching:: One regular expression on each line.
A difference that contains only matching lines is ignored.
Substitutions:: One rule on each line, written as `+regex => replacement+`.
OxideMerge applies the substitutions to both sides before it compares them.
Use them for text that is different in an expected way.
Ignore blocks between start and end lines:: One block on each line, written as
`+start regex => end regex+`.
Differences inside the block are ignored. Use this for a generated section or a license header.

Patterns use the regular expression syntax of the Rust `regex` crate.

==== Managing rules files

.Options → Compare rules
image::rules.png[Compare rules options]

Manage the files in *Options → Compare rules*:

* Choose *None* or a rules file.
  This file is the default for comparisons that do not choose another rules file.
* *New rules file* creates a file.
  *Edit* opens a file in the rules editor, and *Delete* removes it.
* *Open rules folder* shows the folder in your file manager.
  After you change files there, click *Reload*.
* *Import...* adds rules files from other people.
  *Export* saves one file, or all files to a folder (*All rules files to a folder...*).

A folder comparison can use another rules file.
Choose it from *Rules* on the toolbar, or from *Compare → Compare rules*.
*Refresh* (kbd:[F5]) reads the rules file again.

You can also import rules files by dropping them:

* Drop one `.oxrules` file on the window to import it.
  If you drop two, OxideMerge compares them instead.
* Drop any number of `.oxrules` files on the options dialog to import them.

When OxideMerge imports a rules file:

* If a file with the same name and the same rules exists, the new file is skipped.
* If a file with the same name but other rules exists, the new file gets a number in its name.
* If a file with the same rules but another name exists, the new file is added with its own name.

==== The rules file format

Rules files are in the `Rules` folder next to the settings file (see <<configuration>>).
OxideMerge also reads a `Rules` folder next to the program.

A rules file is a JSON file. The name of the rules is the file name without `.oxrules`:

.Build logs.oxrules
[source,json]
----
{
  "description": "Timestamps and generated headers in build logs",
  "ignore_lines": ["^\\[\\d{2}:\\d{2}:\\d{2}\\]", "^// Generated on .*$"],
  "substitutions": [{ "find": "\\b0x[0-9a-fA-F]{8,}\\b", "replace": "0xADDR" }],
  "ignore_blocks": [{ "start": "^/\\* BEGIN LICENSE", "end": "END LICENSE \\*/$" }]
}
----

[[add-rule]]
=== Creating a rule from a text comparison

. In a text comparison, right-click a line and choose *Add compare rule*.
. Choose the kind of rule:
+
--
Ignore lines like this:: A pattern that matches the line, or each side of a changed line.
Substitute:: A substitution that changes the text of one side into the text of the other side.
Ignore block:: A block that starts at this line.
--
. Check the pattern that OxideMerge suggests, and change it if necessary.
. Choose the *Rules file* for the rule, or enter a *File name* to create a new file.

The current comparison uses the rule at once.
Other folder comparisons that use the same file use the rule after you refresh them (kbd:[F5]).

[[filters]]
=== Filters

A filter decides which files and folders a folder comparison includes.
Choose a filter from *Filter* on the folder comparison toolbar.
To manage filters, choose *Tools → Filters...*.

A filter mask is a list of wildcards, separated by `;`.

* A `!` at the start excludes the matching items.
* A `\` or `/` at the end matches folders.

For example, this mask includes Rust and TOML files, and excludes the `target` folder:

----
*.rs;*.toml;!target\
----

OxideMerge also lists WinMerge `.flt` filter files.
It reads them from the `Filters` folder in the configuration folder, and from a `Filters` folder
next to the program.
*Tools → Filters...* shows these filters, opens the filters folder and creates new filters.

[[unpackers]]
=== Unpacker plugins

An unpacker plugin converts a file to text before the comparison.
Use plugins for document formats that need an external conversion program, such as PDF or Office
files.
OxideMerge compares the text that the program writes to its standard output.

To add a plugin:

. Install the conversion program. Make sure that the command can find it.
. In *Options → Plugins*, add an entry with a *File pattern*, such as `*.docx`, and a
  *Command line*.
  In the command line, `${file}` is replaced by the path of the file, with quotes.
. Turn on the entry.

The preset buttons add entries for PDF text (`pdftotext`), Office and OpenDocument files
(`pandoc`) and general document extraction (`tika`).
These entries start turned off.
Move the pointer over the checkbox of an entry to see which program it needs.
This check looks only at the first program name of the command.
If the command fails when it runs, OxideMerge shows the output of the converter.

For example, with Pandoc installed:

----
pandoc -t plain ${file}
----

Converters are used everywhere that files are compared as text: single files, folder comparisons
with *Full contents*, the command line, the file compare pane, *All differences* and the
differences in folder reports.
The size, date, quick and binary folder methods still compare the original files.

Some limits and rules:

* The extracted text is read-only. It can never overwrite the original document.
* Each conversion can run for at most 30 seconds. Each output stream can be at most 16 MiB.
* If the program exits with a nonzero code, this is an error, even if it wrote some text.
* If you stop a folder scan, its conversions stop too.

[[projects]]
=== Projects

*File → Save as project...* saves what the current tab compares in an `.oxmproj` file.
A project stores:

* the paths, the descriptions and the read-only sides;
* the comparison type, the filter, *Include subfolders* and the compare method;
* the compare rules file.

*File → Open project...* opens a project again.
OxideMerge can also open WinMerge projects (`.WinMerge`).

Paths are stored relative to the project file, so you can move a project together with the files.
Paths on another Windows drive stay absolute, and web addresses do not change.

A project does not contain the files. When you open it, OxideMerge loads the files that are at
those paths now.
To move a project to another computer, copy its files and the external rules files that it uses
too.
To share the text as it is now, with your review notes, save a comparison instead.

[[saved-comparisons]]
=== Saved comparisons

*File → Save comparison...* saves a text comparison in an `.oxmcmp` file.
The file contains the text of each side, the bookmarks and comments, and the synchronization
points.

Open the file later, or send it to another reviewer.
It opens read-only, and it does not need the original files.
It is a snapshot of the text: unlike a project, it does not load the current files from their
paths.

[[folder-reviews]]
=== Folder reviews

When a folder comparison has finished, *File → Save comparison...* saves an `.oxmreview` file.
This file is a portable bundle that contains all items that the filter includes.

* To save only some items, select files or folders, right-click and choose
  *Save selected folder review…*. A selected folder includes all of its scanned contents.
* The *Show* settings and the chips only change what you see. They do not remove items from a
  complete bundle.
* Finish all file operations first. If the files changed, refresh the comparison before you save.

To add notes, right-click a file or folder and choose *Toggle bookmark* or *Bookmark comment*.
The name of a bookmarked item starts with `*`, and its comment appears when you move the pointer
over it.
The notes are saved in the bundle, and they appear in HTML, XML and plain-text folder reports.
CSV summaries do not include them.
If you change the notes in an opened bundle, save the comparison again to keep them.

To open a bundle, use any of these:

* the command line: `oxidemerge review.oxmreview`;
* drop the file on the window;
* *File → Open project...*.

The bundle opens as a read-only snapshot, with the comparison options that were used.
It does not need the original files, named filters or external rules files.
Converted documents are stored as their extracted text, and the converter commands are not
stored, so the reviewer does not need the converter programs.
In the tree view, expand the folders to see their contents.

Limits:

* Two or three sides, at most 10,000 items and 256 MiB of uncompressed content.
* OxideMerge refuses symbolic links, special files, paths that are not safe on other systems, and
  files that changed after the comparison.
* A bundle contains the full content of each file, including binary files.

The review workspace adds review decisions to folder reviews. See <<review-workspace>>.

[[html-reports]]
=== HTML reports

To create an HTML report:

. Open a text or folder comparison, and wait until it has finished.
. Check the comparison options, compare rules and folder filters. They change which differences
  the report shows.
. Click *Export HTML* on the toolbar, or choose *File → Export → Export HTML report...*
  (kbd:[Ctrl+Shift+E]).
. Choose the output file. The suggested name is made from the compared names, with `_` in place of
  spaces.
. OxideMerge opens the report in your browser. Check what it contains before you share it.

The report is one HTML file that contains everything it needs.
The recipient can open it in any browser, without OxideMerge.

* Each difference is a card, with line numbers, three lines of context and the changed words
  highlighted.
* The report has summary cards, an index, a side-by-side or unified view, light and dark themes,
  a file filter and search.
* kbd:[N] and kbd:[P] go to the next and the previous difference.
* The report names the compare rules file and counts the ignored differences.
* A folder report includes the differences of each changed text file.

To save reports without opening them, turn off
*File → Export → Open reports in the browser after saving*.

Exporting a report never saves your edits to the compared files.

[[other-reports]]
=== Other reports

*File → Export → Generate report...* writes a report in the format that you choose:

* a folder comparison as HTML, CSV, plain text or XML;
* a text comparison as HTML or XML.

*File → Export → Generate report with file differences...* adds the differences of each changed
text file to an HTML folder report.

*Tools → Statistics...* shows numbers about the current comparison:

* for a folder comparison: the numbers of identical, different and unique files, the errors, and
  the total size of each side;
* for a text comparison: the identical, changed, added, removed and ignored lines, for each pair
  of sides.

==== XML reports

XML reports are for other programs, such as scripts, review tools or a build that checks what
changed.
Choose the `.xml` type when you generate a report, or use `--report <name>.xml` on the command
line.

* A text comparison report lists each difference.
  For each one, it gives the kind, whether it is ignored, and the lines of each side with their
  numbers. The bookmarks and their comments come last.
* The kinds are `changed`, `added` and `removed`.
  Three-way comparisons also use `left-only`, `right-only`, `both-same`, `compatible` and
  `conflict`.
* A folder report lists each file and folder, with its status and its date and size on each side.

[source,xml]
----
<comparison format="1" tool="OxideMerge" version="0.9.8" type="text" created="…">
  <side index="0" role="left" name="a.txt"/>
  <side index="1" role="right" name="b.txt"/>
  <statistics differences="1" ignored="0" identical-lines="1" changed-lines="1" added-lines="0" removed-lines="0"/>
  <differences>
    <difference index="1" kind="changed" ignored="false">
      <lines side="0" start="2" count="1"><line number="2">two</line></lines>
      <lines side="1" start="2" count="1"><line number="2">TWO</line></lines>
    </difference>
  </differences>
</comparison>
----

* Line numbers start at 1.
* If a side has no lines in a difference, its `count` is `0`, and `start` is the line that the text
  would go before.
* The `format` number changes only if the layout changes in a way that could break a program that
  reads it.

[[slideshows]]
=== Slideshows

*File → Export → Generate slideshow report...* saves an HTML page that shows one difference at a
time. Use it to present a change in a meeting or a review.

* The title slide names the compared sides and counts the differences.
* Each difference then has its own slide, with its lines, the lines around it, the changed words
  and any bookmark comments.
* For a folder comparison, there is a slide for each difference of each changed text file.
  The last slide lists the files that are different in other ways, such as binary files or files
  on one side only.
* Ignored differences are not included.

In the browser:

* kbd:[→], kbd:[←], kbd:[Space], kbd:[PgUp] and kbd:[PgDn] go to another slide.
* kbd:[Home] and kbd:[End] go to the first and the last slide.
* kbd:[F] switches to full screen.
* Each slide has its own address, such as `#3` for the third slide, so you can link to it.
* When you print the page, each slide is printed on its own page.

[[patches]]
=== Patches

*File → Export → Generate patch...* writes the differences between two files or folders as a
patch.
Choose the format (*Normal*, *Context* or *Unified*) and the number of context lines.

* You can create patches from two-way comparisons only.
* The ignore options still decide which differences are exported.
* Patches support UTF-8 files, with or without a byte order mark, with LF, CRLF or mixed line
  endings, and files without a final newline.
* Files in other encodings, or with CR-only line endings, must be converted first.
  For these files, OxideMerge shows an error instead of creating a patch that would not reproduce
  the changes.

*File → Apply patch...* applies a unified diff, including the output of `git diff` and
`svn diff`.

* OxideMerge finds each hunk even when its lines have moved. A hunk is one block of changes in the
  patch.
* Each patched file opens next to its original, so you can check the result and save it.
* Hunks that cannot be applied are reported.
  Read these messages and check the comparisons before you save.
  Applying a patch does not save any result automatically.

[[merge-verification]]
=== Merge verification

==== Text files

In a three-way text comparison, open the *Merge verification* tab.

.Merge verification after Preview merge
image::verify.png[Merge verification]

* *Preview merge* shows the result of the merge as a *Read-only preview*.
  It does not change the middle pane.
  Conflicts keep the base text in the preview; you must resolve them yourself.
* *Validate saved result* reads the saved result file again.
  It compares the bytes, the encoding, the byte order mark, the line endings and the final newline
  with the preview.
* If you edit the text, the validation status that is shown is no longer valid.

The preview also warns about merges that apply without conflicts but need a careful review:

* the two sides edit lines that are at most two lines apart;
* both sides change the same setting in different places, such as `name = value`,
  `name: value` or `"name": value`.

A warning does not make the check fail.

IMPORTANT: These checks compare text and bytes only.
They never prove that the merged result is correct.

==== Folders

`--merge-plan` lists the operations and the conflicts of a folder merge.
It does not carry them out.

`--validate-merge` checks a merge result against the plan.
It checks the planned copies, merges and deletions and the files that stay unchanged, and it
checks again that the source files did not change.
The result can be in a separate folder:

[source,sh]
----
oxidemerge --validate-merge result-folder left-folder base-folder right-folder
----

Recommended order: preview the merge, run the merge, then validate the result against the plan.

[[semantic]]
=== Semantic comparison

For JSON, XML, TOML and YAML files, choose *Semantic* to compare the structure instead of the
lines.
Comparing never writes to the files; only the copy buttons described below change a pane.
If OxideMerge cannot read a file, the view shows why, and one click takes you back to the text
view.

.Semantic comparison of two JSON files
image::semantic.png[Semantic comparison]

==== What counts as a change

JSON::
* The order of object keys does not count.
* The order of array elements counts.
* A missing value and `null` are different.
* Duplicate keys are an error.
XML::
* The order of attributes does not count.
* Names are compared with their full namespace.
* The order of child elements, whitespace in text, mixed content and comments all count.
* DTDs, declared and unknown entities, and XML 1.1 are not supported.
  Built-in character references are supported.
TOML and YAML::
* They are compared like JSON: the order of tables and mappings does not count.
* Numbers are compared by value, also between integers and decimals.
  For example, `1` equals `1.0`, and in TOML `8_080` equals `8080`.
* Comments and layout do not count.
* TOML date-times with a time zone are compared by the moment they name.
  For example, `10:00+02:00` equals `08:00Z`.
* YAML follows the YAML 1.2 core schema, so `yes` and `on` are text, and `0777` is the number
  777, not an octal number as YAML 1.1 reads it.
  Keys are compared by value too, so `0x10:` and `16:` are the same key.

Limits:

* A TOML or YAML file can be at most 4 MiB.
* A YAML file must contain one document, without aliases, complex keys or custom tags.
  A core tag such as `!!int` must match its value.

Compare rules for text are not used as filters in the semantic view.

==== Reading the results

Changes are shown as a tree of their paths. Each branch shows how many changes it contains.
Click the source button of a change to go to its line in the file.

Arrays need special care:

* If an array has the same elements in a new order, the elements that moved are listed as
  *Moved*, with their old place.
* To pair the objects of an array by a member instead of by position, type the member name, such
  as `id`, in *Array matching key* (JSON, TOML and YAML).
  An insertion or a new order is then shown as added and moved elements, not as a change at every
  later position.
* If the key cannot pair an array, because an element has no unique simple value for it, a note
  above the changes says so. That array is then compared by position.

Each change tells how its array elements were paired when this was not by path alone: by the array
matching key, as an exact new order, or by position in arrays of different lengths.

A change is marked *ambiguous* when another explanation fits equally well.
Check these changes yourself. Examples:

* In a swap of two elements, either element could be the one that moved.
* A moved element has duplicates.
* An insertion moved the elements, and the change was found by position.

Reports record for each change its `confidence` (`parser_exact`, `array_key`, `reordered` or
`position`), `ambiguous` when it is set, and its `notes`.

==== Copying values

Each change has *Copy value to left* and *Copy value to right* buttons for the panes that are not
read-only. A copy replaces the value on the other side, adds it where it belongs, or removes it
when the source side does not have it.

* Only the text where the value is written changes. Comments, layout and the rest of the file stay
  as they are.
* The edited file is read again before the copy is kept. If the result is not exactly the
  expected structure, nothing changes and the view says why. Edit such a value in the text view.
* Moves are not copied, because a move changes the order of the whole array.
* A copy is one step of *Undo*. The file is written only when you save it.

[[xml-tree]]
==== XML tree view

For two XML files, *Tree* shows both documents as one aligned tree. An element and its
counterpart share a row: the left file on the left, the right file on the right, so both sides
scroll together. A node that exists on one side only has an empty placeholder row on the other
side. The view only reads the files.

image::xml-tree.png[XML tree view]

The column between the sides tells what each row is, also without color: `+` added, `−`
removed, `~` modified, `↕` moved, `•` changes below, and `?` ambiguous. Elements show their
name as written and their `id`, `name`, `key` and `ref` attributes and any changed attributes as
short labels. Expand an element to see its attributes, text, comments and processing
instructions. A folded element with changes inside shows how many, such as *3 changes*.

Rows are paired sibling by sibling below paired parents, so a node is never shown under another
parent:

. by a key rule you give (see below);
. as identical content, keeping the order;
. as identical content out of order, when that content occurs once on each side: a *Moved* row;
. by kind and name between the rows paired so far.

Inserting an element is one addition: the elements after it stay paired with their counterparts.
Because the Semantic view compares by position, it can list more changes for the same files.
What counts as a change is the same as in the Semantic view: attribute order and namespace
prefixes do not count, CDATA is text, and child order, whitespace in text and comments count.
Rows of whitespace-only text that did not change are left out, and whitespace added or removed
next to an added or removed element, such as its indentation, is part of that element.

*Moving between changes*:: The previous and next difference commands (`Alt+↑` and `Alt+↓`,
`Alt+Home` and `Alt+End`) and the buttons above the tree go through the changes in tree order.
A change inside a folded element is not skipped: its parents unfold. *Change 3 / 12* shows where
you are. The filters show and visit only added, removed, modified, moved or ambiguous changes,
and the change counts on folded rows follow the filter. Click a row to select it; the arrow keys
then move up and down and fold and unfold.

*Folding*:: *Expand changes* (also the starting state) unfolds every element with changes inside.
*Collapse unchanged* folds the rest, *Expand to level* unfolds to a depth, and *Reset expansion*
returns to the start.

*Details and source*:: Below the tree, the selected row shows its path on each side (such as
`/catalog/book[2]/@id`), how it was paired, its line and column, its value and the lines of the
file where it is written, as they are in the file. *Show source* opens the Text view at that line.
Choosing *Tree* while the text cursor is in an XML node selects that node.

*Search*:: Type a name or value to show the matching rows with their parents. Text starting with
`/` is a small XPath subset: `/` and `//` steps of element names or `*`, `@name`, `text()` and
`comment()`, with `[@a]`, `[@a='value']` and `[n]` conditions, such as `//book[@id='b102']/title`.
Other XPath is refused with a message.

*Key rules*:: Repeated elements are paired by position unless you give a rule: `book@id` pairs
`book` elements by their `id` attribute, `book@id+lang` by two attributes, and `catalog/book@id`
only below `catalog`. Separate several rules with `;`; they apply once you stop typing. A rule matches local names,
but never pairs elements of different namespaces. Books that swapped places are then shown as
a move plus the content that changed, not as two replacements. A rule is used for a group of
siblings only when every element it covers on both sides has a complete and unique key. Otherwise
a warning gives the number of duplicate and missing keys, and those elements are paired as
without the rule and marked ambiguous. Key rules belong to this view: they do not change the
Semantic view or `--semantic` reports.

*Collections*:: When the selected element holds repeated elements, *View as collection* lists
them as a table: one row each, with a column per attribute, per child element that holds only
text and per attribute of such a child (and one for the text when they hold only text), the value
on each side, and the status. Choose the columns and filter by status; click a row to select it
in the tree. Elements that hold deeper elements or mixed content are flagged, as the table does
not show those.
+
image::xml-collection.png[XML collection table]

Ambiguous rows:: A row is marked ambiguous when another pairing fits as well: several siblings of
the same name on one side with fewer on the other, a key rule that could not be used, an
addition next to an identical sibling, or a swap where either element could be the one that
moved. Check these yourself.

The Tree view is built in the background with progress and *Cancel*, within the same limits as
the Semantic view (100,000 nodes and 64 levels). It is available for two files; three-way XML
comparisons use the Semantic view.

==== Three files

In a three-way comparison, *Semantic* compares the left and right files with the middle one.
Each path that differs is listed once, by its path in the middle file:

* *Only left differs* or *Only right differs*: one side changed it.
* *Both differ the same way*: both sides made the same change.
* *Conflict*: the sides changed it differently, or one side changed a value inside a value that
  the other side changed. Changes to different members of one object do not conflict. When both
  sides changed an array whose elements could be paired in more than one way, such as arrays of
  different lengths paired by position, the whole array is one conflict.

Use the filters to show only the conflicts. *Use left* and *Use right* copy that side's value into
the middle pane, in the same way as *Copy value*. The middle pane is compared as it is now: after
you take a side, that path no longer differs from the side you took.

[[review-workspace]]
=== Review workspace

The *Review workspace* tab of a folder comparison records your review:

* a state for each file and each difference (hunk);
* a *Review comment*, a *Rationale* and optional *Tags (comma-separated)*;
* a name in *Reviewer (free-form name)*. This is free text, not a verified identity.

.The review workspace
image::review.png[Review workspace]

*Next unreviewed* goes to the next file that still needs a review.
To review single differences, open the file from its folder comparison.

To keep your decisions and your position, save the folder review (see <<folder-reviews>>).
OxideMerge saves only after the comparison, the file operations and the check of earlier decisions
have finished. It refuses to save after a comparison that was stopped or that failed.

==== Updating the review

*Update review inputs…* chooses new folders to review against your earlier decisions.
It keeps the selected compare rules, opens the folders read-only and marks the decisions that no
longer match.

* A decision stays with a file that was renamed without changes, and notes the old name.
* If several new files have the same content, each one is marked for a new review.
* Changes to converted content, to converters or to rules can make earlier decisions invalid.
* A decision that is out of date counts as needing action. It never counts as accepted.
* If the context of a difference repeats or is not clear, you must review it by hand.

==== File versions and safety

* OxideMerge saves `.oxmreview` files in version 2.
  It opens version 1 files with every item unreviewed, and refuses unknown versions.
* When you open a bundle, OxideMerge checks the digests of the stored files.
* OxideMerge refuses a bundle with paths that lead outside it, with missing, unlisted or linked
  items, or that a newer version of OxideMerge saved.

[[baselines]]
=== Release baselines

The *Release summary / Compare baselines* panel compares two releases.
It is on the start page, and in the side drawer of a folder comparison.

.A release summary with potential impact turned on
image::baseline.png[Release summary]

Choose each side directly. You do not need to compare two folders first.
Each side is one of these:

[cols="1,2"]
|===
|Source |Meaning

|`folder:PATH`
|The current content of a folder.

|`git:REV:PATH`
|A path in a Git revision.
OxideMerge resolves the revision once and records its commit ID.
Uncommitted changes are not included.

|`review:SIDE:PATH`
|One side of a saved folder review. The first side is `0`.
|===

For Git sources, your Git configuration and filters must be trusted, as for
<<git-revision,Git revision comparisons>>.

==== The summary

The summary counts these kinds of changes:

* added, deleted, modified and unchanged files;
* moves of unique files with exactly the same content;
* suspected renames with edits;
* binary changes and changes of file type;
* semantic changes in JSON, XML, TOML and YAML files;
* excluded files.

It also shows when each side was captured.

* The counts above the list are filters. Click one or more categories to show only those changes.
* *High priority* shows the changes with a risk flag: an important path, or conflict markers that
  are still in a file. These changes are also listed first.
* Select a row to open the captured files read-only.
  The files come from the baseline, even if the sources changed after the capture.

==== Renames

OxideMerge suspects a rename with edits when all of these are true:

* A deleted file and an added file are text files of the same type.
* At least half of their lines, and at least three lines, are the same.
* They are clearly the best match for each other.

The row shows the old name and the share of matching lines.

* Click *Not a rename* to keep the two files as deleted and added.
  On the command line, use `--split-rename PATH`. OxideMerge warns if the path is not an added
  file.
* Click *Detect renames again* to undo this.

==== Important paths

An important path is text that you want to watch, such as `config/` or `api`.
A changed path that contains this text is flagged as high priority.
A file moved or renamed from such a path is flagged too.
Enter important paths in *Important path fragments (separate with ;)*.
On the command line, use `--important-path TEXT`.

`--important-path` and `--split-rename` can be repeated.
They need `--impact`, `--release-report` or `--baseline-left`.

NOTE: Important paths only help you choose what to review first.
They do not guarantee compatibility.

[[impact]]
=== Impact analysis

Turn on *Potential impact* to list the places where the changed files may be used.
Each finding shows the file, the line, a digest of the content and an excerpt.

==== Exact findings

A finding is *Exact* when an import names exactly a file that was changed, deleted or renamed.
OxideMerge recognizes these imports:

* JavaScript and TypeScript: relative imports, re-exports and `require`.
  An import of `./util.js` also finds a changed `util.ts`.
* Python imports.
* C and C++ `#include "…"`, and Objective-C `#import "…"`.
* CSS `@import`.
* Rust `mod name;`, and `use` paths that start with `crate::`, `super::` or `self::`.
* JSON `$ref` file references.

For JavaScript, TypeScript, Python, C, C++ and Rust, OxideMerge reads the imports from a syntax
tree made by Tree-sitter.
A `.h` header is read as C, or as C++ when it can only be read as C++.
For the other files, it reads the tokens of the code.
In Vue and Svelte components, only the `<script>` blocks are read.
So an import can span several lines, and text in a comment or a string is not an import.
If the parser cannot read part of a file, the file is listed as partly assessed, because some
imports and definitions may be missed.

OxideMerge also compares the top-level functions, types and constants of changed JavaScript,
TypeScript, Python, C, C++ and Rust files.
C and C++ global variables are not included.
Rust attributes, such as `#[derive(…)]`, are part of the definition that follows them.

A file that imports a changed or removed definition by name gets an *Exact* finding at the first
place where it uses the name.
The finding tells whether the definition changed or was removed.
Imports under another name count too.
Examples of such imports:

* `import { parse } from "./parser"`
* `from .parser import parse`
* `use crate::parser::parse`

==== Heuristic findings

Heuristic findings are possible uses that need a check:

* the first use of a changed definition name in other files of the same language;
* the name or path of a changed file in the text, as a separate word;
* changed JSON, TOML and YAML keys, also as dotted paths such as `db.timeout`.

If a large change gives more than 500 matches of names and keys, only the first 500 are listed.
A note above the findings counts the others. The other kinds of findings are always complete.

==== What impact analysis does not find

* Imports that are conditional, generated or built by macros.
* Methods, and names used through a namespace, such as `ns.parse`.

OxideMerge never runs builds, tests or scripts of the repository.

==== Working with findings

* Click *Dismiss finding* to hide a finding. This does not change the files.
* In a folder comparison, *Review* opens the file of the finding in the review workspace.
* If there is no result, the panel says that the impact was not assessed.
* Changing a source clears the old findings.
* If you cancel the analysis, no partial result is shown.

[[analysis-limits]]
=== Limits

* Each file can be at most 16 MiB.
* Each baseline can have at most 10,000 items and 256 MiB of captured content.
* Structured files can have at most 64 levels of nesting and 100,000 nodes.
* An impact analysis with more than 2,000 findings fails and asks you to make the scope smaller.
  Only the matches of names and keys are cut to fit.
* Files over these limits are refused or listed as excluded. They are never reported as identical.

Long analyses show their progress and can be canceled.
Some steps, such as parsing one file or merging one file, check for cancellation only before and
after they run, so a cancellation can wait until that step finishes.
These limits do not change the normal comparisons.

[[analysis-command-line]]
=== Running analyses from the command line

[source,shell]
----
oxidemerge --merge-plan left.txt base.txt right.txt --report merge-plan.json
oxidemerge --validate-merge merged.txt left.txt base.txt right.txt --report validation.json
oxidemerge --semantic --format json old.json new.json --report semantic.html
oxidemerge --semantic --array-key id old.yaml new.yaml
oxidemerge --semantic left.yaml base.yaml right.yaml --report conflicts.json
oxidemerge --review-summary review.oxmreview --report review-summary.json
oxidemerge --baseline-left git:v1.0:/repo --baseline-right git:v1.1:/repo --release-report release.html
oxidemerge --impact old-folder new-folder --report impact.json
----

Output:

* Without a report path, an analysis writes versioned JSON to the standard output.
* `.xml` reports, and `.html` reports of most analyses, contain this JSON.
  Their format is separate from the comparison reports.
* An `.html` release report is a readable summary, with the counts, the high-priority changes and a
  section for each change. It also contains the JSON.
* A report cannot replace an input file, and cannot be inside a selected input folder.

Exit codes:

[cols="1,3"]
|===
|Code |Meaning

|`0`
|Identical, or the plan or summary was created successfully.

|`1`
|Different, a warning, conflicts left in a plan, or a review summary with decisions that are out of
date.

|`2`
|An error, or the baseline scope is not complete.
Files that a filter excludes on purpose are outside the scope, so they are not errors.

|`3`
|`--validate-merge` only: the check failed.
|===

Other notes:

* `--format` accepts `json`, `xml`, `toml` and `yaml`.
  The default comes from the extension of the first file.
* Use one analysis option for each run.
* `--semantic` only reports. To copy values, open the files and use the semantic view (see
  <<semantic>>).
* A three-file `--semantic` report lists each path with its `state` (`left`, `right`, `both` or
  `conflict`) and the changes from each side. It exits with `1` when any path differs, including
  conflicts.
* Source positions in semantic results are byte ranges of the decoded UTF-8 text and line numbers
  of the file. They are not offsets in a UTF-16 or legacy-encoded file.

=== Opening comparisons

Run `oxidemerge` without arguments to open the start page.

[[scripting]]
=== Scripting and exit codes

`--cli`, `--report` and `--patch` run without a window. They return these exit codes:

[cols="1,4"]
|===
|Code |Meaning

|`0`
|The content is identical with the current options and rules.

|`1`
|Differences were found. This code is also returned when a report or patch was written
successfully.

|`2`
|An error occurred.
|===

IMPORTANT: Exit code `1` is a comparison result, not an error. Make sure that your scripts treat it
that way.

Folder synchronization (see <<folder-sync>>) has its own codes:

[cols="1,4"]
|===
|Code |Meaning

|`0`
|`--sync-plan`: nothing to do. `--sync-apply`: every change was applied and checked.
`--sync-recover`: everything was undone.

|`1`
|`--sync-plan`: the plan has changes or conflicts.

|`2`
|An error occurred, or the plan was refused and nothing was changed, for example because a file
changed after the plan was made.

|`4`
|`--sync-apply` failed or was stopped, and every change was undone.

|`5`
|Partly applied: some changes could not be undone, also by `--sync-recover`. The journals named
in the output keep the original files.
|===

[source,sh]
----
oxidemerge --sync-plan mirror source destination --report plan.json
oxidemerge --sync-apply plan.json --yes source destination
----

`--sync-apply` compares the folders again and refuses a plan that no longer matches them, one made
with another filter or for other folders, or one written by a newer version.

* The command line uses your saved options, unless you change them with options.
  For runs that must not depend on your settings, set `OXIDEMERGE_CONFIG_DIR` to a separate folder
  (see <<configuration>>).
* Reports are available for text and folder comparisons.
  For a binary or image comparison, OxideMerge prints a message instead of an HTML report.

[source,sh]
----
# Compare without a window. The differences are printed too.
oxidemerge --cli -r dirA dirB

# HTML report of a folder comparison, with the differences of each changed file
oxidemerge -r dirA dirB --report report.html --report-diffs

# HTML report of two files, ignoring changes in comments
oxidemerge old.c new.c --ignore-comments --report diff.html

# Unified diff with 5 lines of context
oxidemerge old.c new.c --patch changes.patch --context 5

# Use a compare rules file
oxidemerge --cli -r build1 build2 --rules "Build logs"
----

In a shell that uses `set -e`, save the exit code explicitly, so that differences do not stop the
script:

[source,sh]
----
result=0
oxidemerge --cli -r old-folder new-folder || result=$?
case "$result" in
  0) echo "No differences" ;;
  1) echo "Differences found" ;;
  *) echo "Comparison failed" >&2; exit "$result" ;;
esac
----

[[integration]]
== Integrating with other tools

[[git]]
=== Git

Install Git and make sure that `oxidemerge` is in your `PATH`.
Then run these commands in a POSIX shell, such as Bash or Git Bash.
They make OxideMerge the diff tool and the merge tool for your user account:

[source,sh]
----
git config --global diff.tool oxidemerge
git config --global difftool.oxidemerge.cmd 'oxidemerge "$LOCAL" "$REMOTE"'
git config --global merge.tool oxidemerge
git config --global mergetool.oxidemerge.cmd \
  'oxidemerge "$LOCAL" "$BASE" "$REMOTE" -o "$MERGED" --dl Local --dr Remote --wl --wr'
git config --global mergetool.oxidemerge.trustExitCode false
----

On macOS, use the full path `/Applications/OxideMerge.app/Contents/MacOS/oxidemerge`, unless you
linked the program into your `PATH`.
On Windows, use the path of `oxidemerge.exe`.

`git difftool`:: Opens each changed file in turn.
`git difftool --dir-diff` opens one folder comparison with all changed files.
In a file, kbd:[Alt+↓] after the last difference opens the next changed file.
`git mergetool`:: Opens a three-way merge with the base in the middle.
Use *Auto merge*, or copy differences to the middle, then save.
The middle pane is written to the merged file, never to the base.
+
With `trustExitCode false`, Git checks whether the output file changed.
If it looks unchanged, Git can ask you whether the merge was successful.
Answer yes only after you saved and checked the result.
Closing the window alone does not mean that the merge was successful.

[[file-manager]]
=== File manager

The *Tools* menu, or `oxidemerge --register-shell`, adds OxideMerge to your file manager:

Windows:: *Tools → Add to Explorer context menu* adds an *OxideMerge* submenu for files, folders,
drives and folder backgrounds.
On Windows 11, it is under *Show more options*.
macOS:: *Tools → Add Finder Quick Actions* adds *OxideMerge: Compare*, *OxideMerge: Select Left*
and *OxideMerge: Select Middle* to the Quick Actions and Services menus of Finder.
Linux:: *Tools → Add to file manager context menu* adds the same entries to Nautilus, Nemo and
Dolphin.

The entries work like this:

* *Compare* compares the two or three selected files or folders.
  With one item selected, it compares the item with the side that you selected before.
  If you did not select a side, it opens the *Select files or folders* dialog with the item.
* *Select Left* and *Select Middle* remember an item, for example from another folder.
  *Compare* then reads *Compare to "name"*.
* *Compare as* (Windows, files only) compares as text, binary, image or web page.

The entries point to the program that added them. If you move the program, add the entries again.
To remove them, use the matching *Tools* command, or run `oxidemerge --unregister-shell`.

|Windows |`%APPDATA%\OxideMerge\config.json`
|macOS |`~/Library/Application Support/OxideMerge/config.json`
|Linux |`~/.config/OxideMerge/config.json`
|===

*Help & Shortcuts* shows where your settings file is.
If OxideMerge cannot read the settings file, it saves it as `config.json.bad` and uses the default
settings. You can then correct the file and put it back.

The configuration folder also contains these folders:

* `Rules`: compare rules files.
* `Filters`: WinMerge `.flt` filter files.
* `Languages`: added or changed language packs.

=== Portable and separate configurations

Portable use:: Create an empty file named `oxidemerge.json` next to the program.
OxideMerge then stores its options in this file, and the `Rules` folder is next to the program.
The program folder must be writable.
Separate configuration:: Set the environment variable `OXIDEMERGE_CONFIG_DIR` to a folder.
OxideMerge then uses the `config.json` in that folder.
This setting has priority over portable use and over the default configuration folder.
Use it for scripts, for tests, or to keep separate work environments.

=== Adding a language

. Copy `lang/en.json` from the source code to a file named `<code>.json`, such as `nl.json`.
. Translate the values. Keep each `{placeholder}` exactly as it is.
. Put the file in a `Languages` folder next to the program, or in the configuration folder.

Messages that are missing, and translations with missing or extra placeholders, are shown in
English.

[[troubleshooting]]
== Troubleshooting

First, read the error message and note the path that it names.
Before you repeat a merge or a save, check the destination, the free disk space, the permissions,
and whether another program changed the file.

=== Installation and startup

macOS refuses to open the app::
Try to open it once, then choose *Open Anyway* in *System Settings → Privacy & Security*.
Or remove the download flag in Terminal:
`xattr -dr com.apple.quarantine /Applications/OxideMerge.app`.

macOS asks for access to a folder::
macOS asks once before OxideMerge reads Desktop, Documents, Downloads, removable volumes or network
volumes. Allow the access, or turn it on later in
*System Settings → Privacy & Security → Files and Folders*.

The AppImage does not start::
Make it executable with `chmod +x`.
If the message mentions FUSE, start it with `--appimage-extract-and-run`.

The window stays empty or does not open on Linux::
OxideMerge draws with OpenGL.
Without a working graphics driver, for example in a virtual machine, start it with
`LIBGL_ALWAYS_SOFTWARE=1 oxidemerge`. This uses the Mesa software renderer.

File dialogs do not open on Linux::
File dialogs use the XDG desktop portal.
Install `xdg-desktop-portal` and the portal for your desktop, such as `xdg-desktop-portal-gtk` or
`xdg-desktop-portal-kde`.

The file manager entries are missing::
On Windows 11, they are under *Show more options*.
The entries point to the program that added them. If you moved or updated the program to another
folder, add them again from the new program.
On Linux, restart the file manager (for example, `nautilus -q`) to see new entries.

The settings are not saved::
OxideMerge tells you why when it cannot save the settings.
Check that the configuration folder (see <<configuration>>) is writable and that the disk is not
full.

=== Editing and saving

A pane cannot be edited::
The pane is read-only for one of these reasons:
+
--
* The lock in its header is closed.
* It was opened with `--wl`, `--wm` or `--wr`.
* It was extracted from an archive.
* It is a JSON or XML file shown formatted.
  Turn off *Format JSON and XML before comparing* to edit and merge it.
--

A file cannot be saved because of its encoding::
The encoding cannot represent some characters in the edited text.
Undo the change that added these characters, and save again.
If you choose another encoding, OxideMerge reads the file again, so copy your edits to another
place first.

A save or copy fails, but the file is writable::
To replace a file, OxideMerge must also be able to create a temporary file in its folder and
replace files there.
Check the folder permissions, the free space, and programs that lock the file.
OxideMerge reports the failure. It never writes directly over the original.
Keep the comparison open until you have saved your edits successfully.

=== Comparison results

Files look identical, but their bytes are different::
Check the options for whitespace, case, line endings, encoding and comments, and the compare rules.
A text comparison can ignore these differences on purpose.
To check that files are exactly the same, use a binary comparison, or the *Binary contents* folder
method.

Files are missing from a folder comparison::
Check the filter, *Skip hidden files and folders*, *Include subfolders* and the *Show* settings.
*Find by name* also hides rows.
*All differences* uses the filter and the display settings of the folder comparison. It does not
include hidden results.

A file is shown as an error::
OxideMerge could not read the file. The message names the file.
Check its permissions. On macOS, also check the folder access described above.

Automatic folder merge does not start, or merges nothing::
Turn on *Include subfolders* and *Include contents of unique subfolders*, and let the comparison
finish.
If a file changed after the comparison, nothing is merged and the file is listed.
If a change fails during the merge, all changes made so far are undone.
Refresh the comparison and review the merge plan again.

=== Web pages

A screenshot mode reports that no browser was found::
The screenshot modes need Edge, Chrome, Chromium or Brave.
Set the browser in *Options → Image / Binary / Web*.

A web comparison is missing content that the browser shows::
The Text, HTML source, Formatted and Resource tree modes use the HTML from the server, without the
content that scripts add.
Use a screenshot mode to see that content.
Content inside frames is not included.
The status bar counts the resources that could not be downloaded, and the resources that were
skipped because they are on this computer or on a private network.

=== Performance

Large files are slow or use a lot of memory::
A text comparison keeps the decoded text, the comparison data and the edit history in memory.
The memory use depends on the content and on what you do.
Binary and image views also load the complete files.
+
--
* Valid UTF-8 files of 16 MiB or more load in parts.
  UTF-16 files and legacy encodings are decoded completely.
  The text stays editable, and the compare rules work as usual.
* Syntax highlighting is turned off above 50,000 lines or 16 MiB of decoded text.
* Editing, undo, word wrap and unusual compare rules can still use more memory.
--
+
To use less memory, use a binary comparison, or compare folders by size and date instead of by
content (see <<compare-methods>>).

[[limitations]]
== Known limitations

* Archives: ZIP-based formats, TAR (plain, gzip, bzip2 and xz) and 7z are supported.
  RAR is not supported. Extracted archive contents are read-only.
* Text editing is line-based. It is intended for reviewing and merging changes.
* Unpacker plugins use external commands. WinMerge plugin DLLs and scripts are not supported.
* Web page comparison does not support cookies or logins. A page that needs a login shows its login
  page.
  Only the screenshot modes run page scripts. In the other modes, content that scripts add is
  missing.
  Content inside frames is not compared.
* Semantic comparison copies one value at a time, and only when the edit can be confirmed by
  reading the file again. It does not move array elements or merge all changes at once.
* Folder synchronization works on local folders only, and only when you start it.
  A renamed file appears as a deletion and a copy.
* The translations were made with the help of machines and have not been reviewed by native
  speakers.
